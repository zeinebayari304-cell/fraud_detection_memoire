3. Utiliser l'application

En bas de la barre latérale, l'état de l'API est affiché (« API connectée · Random Forest »).

Tableau de bord

Vue en direct de ce qui a été analysé dans l'application : transactions analysées, fraudes signalées, taux, activité sur 7 / 30 / 90 jours, dernières alertes, état des modèles. Il se rafraîchit tout seul toutes les 15 secondes. Après une installation neuve, tout est à 0 tant que rien n'a été analysé.

Analyse de transaction

  1. Choisissez le modèle (un modèle dont le fichier manque affiche « (non chargé) »).
  2. Remplissez les 30 champs à la main, ou utilisez le panneau Jeu de données au-dessus du formulaire : Importer creditcard.csv (si le fichier n'est pas encore dans data/raw/), Fraude aléatoire, Normale aléatoire, un numéro de ligne, ou le tableau (filtres classe et sous-ensemble Test / Validation / Entraînement, puis Utiliser).
  3. Cliquez sur Analyser la transaction : verdict, probabilité de fraude, niveau de risque, seuil. Si le score atteint le seuil, une bannière « ⚠ Alerte de fraude » s'affiche.
  4. Pour une ligne du jeu de données, le résultat indique aussi sa classe réelle (prédiction correcte, fraude manquée ou fausse alerte).
  5. Comparer tous les modèles note la même transaction avec chaque modèle chargé.

Analyse CSV

  1. Glissez un CSV contenant au moins Time, V1…V28, Amount (les autres colonnes, comme Class, sont ignorées ; 5 Mo maximum).
  2. Choisissez le modèle, cliquez sur Lancer l'analyse.
  3. Filtrez les résultats (Toutes / Normale / Fraude suspectée) et cliquez sur Exporter les résultats CSV.

Pour le modèle final, le résultat attendu est TP 56 / FP 7 / FN 15, et la page indique si l'application est identique au mémoire.

Comment une prédiction est calculée

  1. Amount devient log1p(Amount) (même transformation que le notebook 02).
  2. Les 30 colonnes (Time, V1…V28, Amount) passent dans le scaler MinMax.
  3. Le modèle renvoie une probabilité de fraude.
  4. La transaction est signalée si la probabilité est supérieure ou égale au seuil (0,5 par défaut, la règle native des modèles).

Critères de réussite. Les trois contrôles de justesse sont 3.6, 4.2 et 8.11. S'ils passent, la chaîne de prédiction est correcte et reproduit le mémoire. Le reste vérifie la gestion des erreurs et la stabilité.

6. Limites et suite

  • Les modèles ont été évalués sur un seul jeu de données (transactions par carte européennes, 2013) : rien n'est garanti sur d'autres données.
  • Les chiffres de robustesse adversariale viennent de petits panels d'attaques (environ 53 fraudes attaquées) : ce sont des observations empiriques, pas des garanties certifiées.
  • L'application est un outil de recherche et d'aide à la décision : une transaction signalée doit être vérifiée.
  • Pas encore implémenté (prévu d'après le diagramme de cas d'utilisation) : connexion / déconnexion JWT et rôles (Analyste, Expert, Administrateur), historique des analyses par utilisateur avec export, journal d'audit, gestion des utilisateurs.
